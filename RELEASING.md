# Releasing NetDash Toolkit

A release is a tag push. Everything downstream (3-OS Electron builds, SLSA provenance, attestations, SBOM, checksums, release notes, the Homebrew cask bump) is automated by [release.yml](.github/workflows/release.yml). This runbook exists because the pipeline gates hard, and knowing why each gate exists saves you a failed run.

## 0. Preconditions

- You are on `main`, clean tree, and `main` CI is green for the commit you are about to tag.
- Local `pnpm validate` passes (`typecheck`, `lint`, `format:check`, `test`, `build`). CI runs the same chain; if it fails locally it will fail there.
- No half-merged Dependabot PR sitting open that you meant to include.

## 1. Bump the version everywhere

The pipeline hard-fails if the tag and `package.json` disagree (artifact filenames embed the package version while release notes and cask URLs derive from the tag; a mismatch would publish verification commands pointing at files that don't exist). Grep first, because a location has been missed before:

```bash
grep -rn "3\.0\.1" package.json CHANGELOG.md data/changelog.json
```

Update:

1. `package.json` `"version"` field.
2. `CHANGELOG.md`: move `[Unreleased]` content under a new `## [X.Y.Z] - YYYY-MM-DD` heading.
3. `data/changelog.json`: add the release as the first entry. `components/header.tsx`
   renders `releases[0].version` as the in-app badge, so skipping this ships the
   previous version's number on the new build. It happened once: v3.0.0 showed on
   a 3.0.1 build. `tests/unit/metadata.test.ts` now fails if the two disagree.

NOT the version (do not touch): `Casks/netdash.rb` (regenerated by the pipeline), anything under `.github/workflows/` (tag-derived), README badges (dynamic).

## 2. Commit, tag, push

```bash
git add package.json CHANGELOG.md
git commit -m "chore(release): bumped version to X.Y.Z and updated changelog"
git push origin main
git tag vX.Y.Z
git push origin vX.Y.Z
```

Prerelease tags (`vX.Y.Z-rc.1`) work: the release is marked prerelease and the Homebrew cask bump is skipped. `package.json` must still match exactly (`X.Y.Z-rc.1`).

## 3. What the pipeline does

`validate` (tag format, quality gates, tag-vs-package.json guard) -> `build` (3-OS matrix, hermetic, macOS codesign gate) -> `combine-hashes` -> `provenance` (SLSA Build L3 via the slsa-framework trusted reusable workflow) -> `publish` (draft release with generated notes + verification footer, all 11 assets, GitHub native attestations, SBOM, then published once) -> `homebrew` (cask regenerated from the publish job's own hash outputs and pushed to `main` with `[skip ci]`).

Draft first, always: the release is created as a draft and published exactly once with every asset attached, which keeps the pipeline compatible with GitHub immutable releases if that setting is ever enabled.

## 4. After the run

Verify like a user would, not by trusting the green check:

```bash
gh release download vX.Y.Z -p "checksums.txt" -p "NetDash-Toolkit-X.Y.Z-mac-arm64.dmg" -p "*.intoto.jsonl"
shasum -a 256 -c checksums.txt --ignore-missing
gh attestation verify NetDash-Toolkit-X.Y.Z-mac-arm64.dmg --repo sunnypatell/netdash-toolkit
slsa-verifier verify-artifact NetDash-Toolkit-X.Y.Z-mac-arm64.dmg \
  --provenance-path netdash-toolkit-vX.Y.Z.intoto.jsonl \
  --source-uri github.com/sunnypatell/netdash-toolkit --source-tag vX.Y.Z
```

Also confirm the `chore(homebrew): auto-update cask to vX.Y.Z` bot commit landed on `main`, and pull it locally.

## 5. Release-notes house style

The generated section (categorized merged PRs) is automatic. The verification footer is templated. If you edit the body afterwards: all lowercase, bullets open with a **bold claim.** followed by mechanism, spaced hyphens instead of em dashes, links to primary sources, no hype words. Thank the reporter above the star line when a release closes someone's issue.

## 6. Fixing a botched release

The v3.0.1 release took three attempts; this section is the distilled memory.

- The pipeline failed before `publish` (no release exists yet): fix the problem on `main`, then move the tag and push it again. The tag ruleset blocks deletion for non-admins; as admin you bypass with a warning, which is the intended escape hatch.

  ```bash
  git tag -d vX.Y.Z && git push origin :refs/tags/vX.Y.Z
  git tag vX.Y.Z && git push origin vX.Y.Z
  ```

- The pipeline failed during `publish` (partial release exists): re-run the failed jobs from the Actions UI. The publish job is idempotent (`gh release upload --clobber`, notes refreshed on re-run) and `overwrite: true` on build artifacts makes full re-runs safe.
- The release published but an asset is wrong: do not edit assets in place. Ship a patch release. Checksums, provenance, and the cask all reference exact bytes; a swapped asset breaks every verification path.

Known gates that have fired for real, and what they mean:

| gate                                                | what it caught                                                                                                                                                               |
| :-------------------------------------------------- | :--------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `codesign --verify --deep --strict` on the mac legs | electron-builder ad-hoc signs arm64 only; x64 shipped unsigned for every release before v3.0.1. The `afterPack` hook now seals both; if this gate fires, the hook regressed. |
| `format:check` in validate                          | a file class the pre-commit hook didn't cover (`.cjs` was the gap; the lint-staged globs now include it)                                                                     |
| tag-vs-package.json guard                           | tagging without bumping `package.json`                                                                                                                                       |

## 7. Maintenance that is NOT per-release

- Action SHA pins: Dependabot bumps them monthly in one grouped PR.
- `FIREBASE_SERVICE_ACCOUNT` secret: only needed if Firestore rules change; the deploy job skips green without it.
- Scorecard, CodeQL, and dependency review run on their own schedules; they never block a release.
